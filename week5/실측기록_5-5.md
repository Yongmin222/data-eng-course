# 5-5 실측 기록 — 파티셔닝과 셔플링

로컬 Docker Compose 클러스터(Spark 3.5.3, 마스터 1 + 워커 2, 총 코어 4)에서 직접 잰 값입니다. 데이터는 `spark.range(1, 10_000_001)`(1천만 행)이고, 시간은 모두 1회 측정입니다. 데이터가 작아서 절대값보다 방향을 봐야 합니다.

## 1. 기본 파티션 수

| 확인 방법 | 결과 |
|---|---|
| `df.filter("id % 7 = 0").explain()` | `Range (1, 10000001, step=1, splits=4)` → 파티션 4개 |

- 기본 파티션 수는 클러스터 코어 수(4)에 맞춰 잡혔습니다. 파티션 4개 = 태스크 4개 = 코어 4개가 동시에 처리합니다.
- 실행 계획에 `Exchange`가 없고 `*(1)`만 있어서, filter는 셔플 없는 좁은 변환이며 Stage 1개로 끝납니다.

## 2. 좁은 변환 vs 넓은 변환

| 작업 | 실행 계획 | 셔플 |
|---|---|---|
| `filter` | `Filter` → `Range` (Stage 1개) | 없음 |
| `withColumn` + `groupBy("b").count()` | `Exchange hashpartitioning(b, 200)` 포함 | 있음 |

- `groupBy` 계획에는 셔플 전에 `HashAggregate (partial_count)`가 먼저 있습니다. 보내기 전에 파티션 안에서 미리 세어 두어, 1천만 행이 아니라 요약본만 네트워크로 보냅니다.
- b 값은 10종류인데 셔플 후 파티션은 기본값 200개로 잡힙니다. 대부분 빈 파티션입니다.
- 결과는 bucket 0~9가 각각 1,000,000개로 나왔습니다.

## 3. 셔플 파티션 수와 AQE (200 vs 8)

같은 `groupBy`를 `spark.sql.shuffle.partitions`와 AQE(`spark.sql.adaptive.enabled`)를 바꿔 가며 측정했습니다. 첫 실행은 워밍업이라 제외했습니다.

| AQE | shuffle.partitions | 시간 |
|---|---|---|
| 켜짐 | 200 | 0.13초 |
| 켜짐 | 8 | 0.17초 |
| **꺼짐** | **200** | **0.89초** |
| 꺼짐 | 8 | 0.14초 |

- AQE를 끄고 200개로 두면 데이터 10종류를 처리하려고 빈 태스크 200개를 모두 실행해서 가장 느렸습니다(약 6배).
- AQE가 켜져 있으면 실행 중에 빈 파티션을 알아서 합쳐 주어 200이어도 빨랐습니다.
- 파티션 수를 8로 직접 줄이면 AQE 없이도 빨랐습니다.
- 결론: 파티션 수는 데이터 크기에 맞춰야 하고, 못 맞춰도 AQE가 어느 정도 보정해 줍니다.

## 4. 스큐(쏠림)

`repartition(4, "k")`로 키가 같은 행을 같은 파티션에 모은 뒤 같은 계산(`sha2` 해시)을 했습니다. 키 분포만 다르게 했습니다.

| 데이터 | k 분포 | 시간 |
|---|---|---|
| 고른 분포 | `id % 100` (0~99 각 1%) | 0.63초 |
| 스큐 | `id % 10 < 9`이면 0, 아니면 `id % 10` | 0.96초 |

스큐 데이터의 k는 사실상 0(90%)과 9(10%) 두 가지뿐입니다. Spark UI(Stage 상세)에서 확인한 태스크 분포는 아래와 같습니다.

| 지표 | Median | Max |
|---|---|---|
| 태스크 Duration | 75 ms | 0.6 s (약 8배) |
| Shuffle Read Records | 0 | 10,000,000 |

- 4개 태스크 중 **하나가 1천만 행 전체를 읽었고**, 나머지 셋은 0행이었습니다. 두 키가 해시로 같은 파티션에 떨어졌기 때문입니다.
- 한 태스크가 끝날 때까지 전체 Stage가 기다립니다. 일의 총량은 같아도 분배가 쏠리면 느려집니다.
- 데이터가 작아서 시간 차이는 1.5배 정도지만, 데이터가 커지면 격차가 벌어지고 쏠린 파티션은 메모리 부족으로 죽을 수 있습니다.

## 5. coalesce로 저장 파일 수 줄이기

| 저장 방식 | 경로 | parquet 파일 수 |
|---|---|---|
| 파티션 4개 그대로 저장 | `test-narrow/` | 4 |
| `coalesce(1)` 후 저장 | `test-one/` | 1 |

- 파티션 하나가 파일 하나가 됩니다. 저장 직전에 `coalesce`로 합치면 작은 파일이 쏟아지는 것을 막을 수 있습니다.
- `coalesce`는 셔플 없이 이웃 파티션을 합치므로 수를 줄이기만 합니다. 아주 큰 결과에 `coalesce(1)`을 쓰면 한 태스크가 전부 떠안으므로 데이터 크기를 보고 정해야 합니다.

## 6. 정리

| 증상 | 확인한 곳 | 처방 |
|---|---|---|
| 한 태스크만 오래 걸림 | Stage 상세의 Task Duration Max/Median | 키 분포 확인 (스큐) |
| 빈 태스크가 많음 | 계획의 `Exchange ..., 200` | shuffle.partitions를 데이터 크기에 맞게 |
| 작은 파일이 많음 | 저장 직전 파티션 수 | `coalesce`로 정리 |
